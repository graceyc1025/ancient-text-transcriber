# 大量□、有效文字极少：专项诊断

2026-10-15（北京时间）。检查基线：`5de06b1`（已合并 `feat/vertical-ocr-diagnostics` 的 main），诊断在独立分支进行，不自动合并或部署。

## 当前结论

本地真实浏览器复现的□主要来自**前端置信度标疑**，不是原始OCR文本里的方框，也不是UTF-8编码或字体缺字。模型确实加载成功，但其原始输出本身有错识；把阈值调低只会显示更多候选字，不能证明原文识别更准确。

同一现代30字图整页、自动分栏、人工单栏在默认PSM5下没有发现前端丢字；PSM6用于竖排单栏则明显变差。未核定年代的手稿在分栏后输出增加，但汉字数量反而下降，说明增加检测数量不能当作识别改善。

没有用户本次故障原图、浏览器存储和日志；以上结论针对仓库源码及实际执行的样本，不能远程证明所有用户设备的缓存都正常。

## 模型、路径与缓存

- `chi_tra_vert`，OEM LSTM_ONLY，非SIMD LSTM WASM；自动竖排对应PSM字符串`"5"`，横排才使用`chi_tra`/PSM6。
- 首次模型请求实际路径为 `/ancient-text-transcriber/ocr/tessdata/chi_tra_vert.traineddata.gz`，响应200。Worker和核心也来自同一项目路径，无第三方OCR请求。
- 不只查看配置或页面“加载完成”：通过Worker公开FS接口取出**实际加载的解压模型字节**，计算SHA-256为 `bbe518f94b9e3852109113507357bfe7e257834d88d2d1ead44178046bcd2181`，与 `models/manifest.json` 一致。IndexedDB中的模型字节也与该哈希一致。
- 浏览器缓存为 `keyval-store` 数据库、`keyval`对象仓库，键为 `ancient-transcriber-tessdata-best-e12c65a9/chi_tra_vert.traineddata`；固定上游提交区分模型版本。用新Worker重做识别，热缓存时无模型下载请求，结果与冷启动逐字相同。
- 构建时的模型SHA校验不等于每个用户设备的运行时缓存校验。生产代码目前不对每次缓存读取计算哈希；本次审计单独计算。不能据此承诺任意被损坏/人为覆盖的缓存都能正常识别。
- 线上页面在本环境访问返回403，本次不宣称核实了线上资源、HTTP缓存头或用户浏览器的实际部署版本；本地子路径真实加载和生产构建测试另行验证。

### 确认并修复的错误：初始化失败被拖成两分钟超时

在**隔离的浏览器上下文**主动注入两种故障：模型请求返回404；IndexedDB缓存替换为两字节无效内容。它们是故障测试，不是声称用户缓存已经损坏。修复前两种情况都直到120秒应用超时才失败，没有任何已完成的识别记录或生成文字。

根因在锁定的Tesseract.js 7.0.0：语言下载及API初始化的reject消息使内部任务拒绝，但createWorker返回的初始化Promise只对`load`动作直接拒绝；后续链的catch吞掉了失败。项目原来的空errorHandler及超时兜底使这些失败只呈现为“模型加载超过两分钟”。

最小修复是新增 `public/ocr/bootstrap-worker.js`，成功消息及识别字节原样通过；仅将loadLanguage/initialize的致命reject通过库已处理的原生Worker错误事件传出，并关闭失败Worker。`src/ocr.js`只改Worker入口路径。没有改模型、阈值、裁切算法或PSM默认值；将来升级Tesseract时应复核此兼容层。

修复后同一故障审计：404在119毫秒返回含URL和404状态的错误；坏缓存133毫秒返回`initialize: initialization failed`（本机测量，不是速度承诺）。新增2组生产构建浏览器测试，验证15秒内报具体错误、既有人工底稿保留、不伪造识别记录，以及解除404/清理坏缓存后真实OCR可重试成功。正常路径的11种整页/单栏/PSM/手机预算/手稿对照，在修复前后原始文本、标疑文本和模型/缓存哈希**逐项相同**。

此修复改善故障可诊断性，**不提高成功加载模型后的字形识别准确率，不是消除大量□的精度修复**。

## □从哪里来

`src/transcription.js` 的 `parseTSV` 对每个level5字词读取置信度：低于阈值65，或置信度不是有限数时，以检测文字的Unicode码位数生成`'□'.repeat(characters)`。这是预期的标疑规则，可能把成组字词里正确的字也一起遮住；它不是逐字准确性判定。

页面声明UTF-8，原始结果先作为JavaScript字符串传入记录，随后用textarea.value显示；没有GBK转换或简繁转换。直接检查字符串中的U+25A1、U+FFFD，可以区分真正的□、编码替代字符�和字体绘制的缺字框。本次所有原始OCR样本的U+25A1和U+FFFD都为0。其他设备的罕见字仍可能因为系统字体不覆盖而显示缺字框，但那不会把复制出来的汉字变成U+25A1。

不要以阈值0当作研究定稿。可在现有“原始OCR输出与识别记录”查看候选文本，保留默认标疑底稿、原图及JSON，逐字校对。

例：整页中原本正确识别的“亦”置信度为0，仍被规则标□；原文“慍”被误认成“惱”，置信度69.880669，超过阈值而保留。置信度不是正确率，不能直接用它确定哪些字可以引用。

## 同图真实测试

`scripts/diagnose-squares.mjs` 启动带项目子路径的Vite服务，在真实Chromium中调用仓库的BrowserOCR；原始内容直接来自 `worker.recognize`。读取实际模型及缓存字节，不替换识别方法或预置输出。审计原始TSV汉字数与整理后汉字数，二者在本次所有样例相同。

### 版面和PSM

单栏使用等宽三分区域，从右向左：`[2/3,0,1/3,1]`、`[1/3,0,1/3,1]`、`[0,0,1/3,1]`；对应9/10/11字。原图字形保持直立，没有先把整栏旋转为横排。三栏PSM5合计与整页的原始文本和标疑结果一致；自动分栏也没有恢复丢失字或提高这个样本的准确率。

同一个右栏改用PSM6，原始汉字从9降至7，7字全部低置信度而被标□；这属于页面分割/识别模式不适合该图，不能以PSM6替代竖排默认。PSM3对这个清晰样例与5相同；此前手稿单列的PSM3/5差异不代表3对所有古籍更好。

投影自动切线仍可能切到笔画、把印章/版框当列；裁切边界会改变引擎检测。复杂古籍需对照检测框，并保存同一框的原始结果比较。保留现有分栏与预处理选项，不强制用另一参数掩盖模型误识。

### PaddleOCR.js具体可行性与代价

核对官方源码提交 `dab3fe35379033fdcb2d0e9572fac0b36c9a9ebf`，SDK包 `@paddleocr/paddleocr-js` 0.4.2，Apache-2.0，npm元数据解包约23.8MB（**不是完整网站下载量**，还不含全部依赖、模型与运行时）。代码确认可用`backend: "wasm"`、`numThreads: 1`及自定义`wasmPaths`；不是必须购买在线OCR或API Key。

满足现有隐私约束需要把默认第三方模型URL、ORT运行时等改为本站静态资源并锁定版本/校验模型，不照抄默认CDN配置。模型包要求未压缩ustar tar，包含`inference.onnx`及`inference.yml`且model_name匹配；不能把任意`.traineddata`或Paddle训练权重直接传入。

GitHub Pages不能仅靠HTML的meta标签设置COOP/COEP响应头，多线程WASM通常依赖跨源隔离。应先测单线程WASM，WebGPU仅作可用设备的可选路径，不要求所有手机提供WebGPU。Worker、ONNX/WASM资源须遵守现有CSP及项目子路径；仍需实际构建、实机内存和长图测试。

源码裁切逻辑会将高宽比≥1.5的检测块逆时针旋转90度，检测框默认按上到下/左到右排序。这些行为不能直接当作清代右至左列序保证；需要对直立竖排字形、夹注和版心单独验证并保留现有人工分区/列序控制。识别分数过滤也会造成少输出，替代对照必须保留被过滤前候选和检测框。

最小下一步是独立实验页面，用同一批有来源的清代原图和人工真值比较检测漏列、字符替换/删除/插入、列序、下载体积、时间和峰值内存；通过之后再决定是否作为第二引擎。此次不接入、不改变正式OCR，不使用付费API。

## 复现与证据边界

维护者运行（网站使用者无需安装）：

```bash
npm ci
npm run build
node scripts/diagnose-squares.mjs
# 可选：加入已有本地扫描，不提交或部署它
OCR_DIAGNOSIS_OUTPUT=/tmp/square-diagnosis.json node scripts/diagnose-squares.mjs tests/samples/local/page_2.png
npm test
npm run test:e2e
```

脚本使用5176端口，默认输出`test-results/square-diagnosis.json`，包括原始文本/TSV与模型哈希。Playwright会清理test-results，先保存需要的审计数据。现代演示图不是清代古籍；手稿的年代和版本未经核定，缺完整人工真值。手机预算仅通过桌面Chromium参数复现，不是手机实机精度评测。

本轮验证：18项单元测试通过；模型校验和静态构建通过；7组生产构建浏览器测试通过（原有5组及新增2组初始化失败/重试）。真实OCR审计共11种情况及2种故障注入通过。没有更换引擎、扩大重构、合并main或发布网站。
