# PaddleOCR 正式网站集成可行性评估

日期：2026-10-17（北京时间）。分支：`experiment/paddleocr-v5-browser`。本轮只评估并补充隔离浏览器诊断，未改正式入口、识别算法、模型、参数、依赖或部署配置；没有合并 main、运行发布或针对两张古籍调参。

## 结论与采纳范围

**免费、纯浏览器、GitHub Pages 静态部署在技术上可行；当前实验实现尚不适合直接接入正式网站，尤其不能承诺手机稳定。** 建议下一阶段保留 Tesseract 为现有默认，新增明确标为试用的 Paddle 可选项。用户选择 Paddle 后默认整页/整区识别，沿用已冻结的模型及几何阅读序，不自动分栏补白、不按底本改字。手机的默认引擎暂不改为 Paddle。

两份真实古籍中，Paddle 整页 CER 分别为 12.36%、22.50%（第二份底本待复核，为暂定值），均优于对应 Tesseract；这支持继续集成验证，不足以代表全部清代刻本、行书、异体字或手机。补白分栏不是普适提升方案，不能作为正式整页识别前的隐式步骤。

当前采纳阻碍是主线程阻塞、较高内存、CSP 不兼容以及 Worker 内嵌运行时版本差异。必须先完成故障隔离及真机验收，再决定是否提交集成 PR；本轮没有实施这些产品改动。

## 本轮实际检查与边界

检查根目录 `src/app.js`、`src/ocr.js`、`src/images.js`、`index.html`、Vite、Pages 工作流，以及实验 `engine.js`、prepare、模型清单、SDK 实际分发代码和现有测试记录。实验识别代码保持在 `8817b25`。

新增诊断在 Linux Chromium 154.0.8037.57 上运行，使用本机只读静态服务的 `/ancient-text-transcriber/experiments/paddle/` 子路径，无 COOP/COEP，`crossOriginIsolated=false`。以既有道光本正文副本进行整页运行，不导入标准文本、不重新计算 CER。Worker 实验也使用同一正文、相同 2607×1917 工作尺寸及冻结检测参数。另一次现代演示图仅验证 Worker 能执行，不作为古籍准确率证据。

数字摘要见 [PaddleOCR正式集成评估数据.json](PaddleOCR正式集成评估数据.json)。完整诊断脚本和网络记录在本轮下载包中；不公开用户图片、标准文本或完整 OCR 文字。

## 建议集成结构（尚未实现）

### 选择、按需加载与生命周期

保留现有 Tesseract 模型、PSM、预处理、分区和人工校对能力；引擎选择增加 `Tesseract（现有）`、`PaddleOCR（试用）`。同一批任务固定引擎，运行时不能交叉初始化。

建立轻量协调器和两个适配器，统一 `initialize / transcribe / cancel / release`，返回现有 `segments / passes / columns / warnings / settings`。Paddle 需要适配记录、检测框、历史窗口，不能把实验 `recognize()` 的返回值直接塞进正式 `BrowserOCR.transcribe()` 调用点；`record.model/psm` 等 Tesseract 专属展示要区分引擎，不能伪造 PSM。

在首次实际识别时动态 import 所选适配器，然后加载该引擎资源；不预取另一引擎，不把两个引擎打进必下的共享大包，不用 Service Worker 预缓存两套模型。当前根入口静态 import Tesseract；以后要达到“未选择引擎连其代码也不下载”，这处需要改为动态加载，不能只加一个下拉框。

协调器串行管理 `idle → loading → ready → recognizing → cancelling/error`。切换引擎先停止队列、让旧任务失效、终止旧 Worker，再允许新初始化；以递增任务ID丢弃迟到结果，避免旧引擎覆盖新编辑。释放模型不等于模块卸载：主页面动态 import 的模块不会因 `dispose()` 自动卸载，WASM 内存/GC也没有立即回收保证。因此重型运行时应尽量放入可整体销毁的 Worker，而不是长期留在编辑页。

### Paddle 整页与阅读序

先沿用已验证的 PP-OCRv5 mobile 检测/识别权重、官方字典、识别分数阈值0、整页参数，保留全部 SDK 原始项、坐标、分数、原生框序及独立的几何序文本。默认不继承 Tesseract 的65阈值标□功能；不把行置信度当作逐字正确率。

同一竖排区域采用现有 `sortItems` 的几何规则：列从右至左，同列上至下；双页一般先右页、后左页。第二页样本的原生框序暂定 CER 为79.17%，几何重排后22.50%，所以直接拼接 SDK 文本不可接受。该排序不使用标准文本或语境，也不能保证处理跨栏框、标题、夹注、版心或混合横排。保留已有手动分区/排序能力，按区域分别排序，并允许人工校序；自动版面分类不列入首阶段承诺。

记录当前引擎/模型哈希、版本、工作尺寸、区域坐标和实际参数。人工编辑只改底稿，不改原始结果；繁简、异体字保持实际候选，不自动归并或补字。「淂」「扵」等不在冻结字表内的形式依然需要人工处理，集成本身不会改善字表覆盖或行书准确率。

## 静态部署与免费条件

可复用根 Vite `base:'./'` 和 Pages Actions 的静态 artifact。模型、SDK、ORT模块/WASM、字典及许可一律随构建同源托管，不用运行时CDN、API Key、后端、Python或数据库。模型可能需要下载，不等于上传用户图片；断网首次访问没有模型时应如实失败，不能承诺离线首次可用。

当前根构建/根 lockfile/Actions **没有纳入实验子项目**。实验模型目录被忽略，`prepare.mjs` 在缺模型时只生成不可用状态仍可能成功构建，不能直接当正式模型供应链。以后应：固定依赖与社区包来源，在CI获取校验过的权重，按固定流程生成tar并验证哈希；缺失、字典不匹配或损坏必须使正式构建失败。保留模型导出来源和许可，不能把社区导出包称作与未取得官方包逐字节相同。

固定模型tar合计 **21,572,608字节（约21.57MB）**。本轮主线程冷页面请求到的唯一静态文件未压缩体积约54.43MB，SDK Worker古籍路径约65.38MB；不是手机流量或 Pages 实测传输量。现有产物还有未用/重复ORT资源，应先查依赖图再减重，不得凭文件名删除实际要用的WASM。大模型每次无需重复发布更换，但仍受GitHub及用户流量/存储条件约束。

Worker、模型、`.mjs`、`.wasm` 路径都以项目根 `import.meta.env.BASE_URL` 解析为绝对同源URL后传入 Worker，避免依赖 Worker 中不存在的 `document` 或从 `/models/` 误跳域名根。用 `.js` Worker、`.mjs` ORT入口及正确 `application/wasm` MIME，保留相对代码分块路径；用户实际站点的HTTPS、MIME与缓存行为仍需以后验证，本轮未上线Paddle。

继续 WASM 单线程、batch=1、明确同源 `wasmPaths`，不依赖WebGPU或共享内存，不要求无法在标准Pages直接配置的COOP/COEP。文件名带 `threaded` 不表示单线程配置必须跨源隔离，本地非隔离运行已有实测；仍需在支持的手机浏览器核验WASM特性。

### 两项具体兼容性阻碍

1. **内容安全策略。** 根页面只允许 `wasm-unsafe-eval`，OpenCV的当前构建还使用JS动态求值。本轮以根CSP替换实验CSP，主线程及SDK Worker路径都真实失败。不能仅设置 `worker:true` 就声称兼容。应评估将重型载入及所需CSP局限在OCR隔离入口/受控Worker，或使用不需动态求值的兼容构建；若仍需放宽编辑页到 `unsafe-eval`，须明确这是安全策略取舍并验证所有用户文字仅用安全DOM输出。本轮未改任何CSP，也未验证替代构建可用。
2. **Worker内嵌运行时。** SDK 0.4.2分发的Worker实际内嵌ORT **1.24.3**，而现有主线程和静态WASM固定 **1.22.0**。本轮Worker使用已有1.22.0资源能跑通一次，但这不证明跨版本兼容可靠。SDK未设置 `wasmPaths` 还会回退外部CDN。正式接入前必须消除版本含糊，固定Worker JS与WASM匹配的版本并重新检查模型输出/稳定性；或评估在自有Worker内复用已固定的运行时。不得悄悄换版本后继续引用原CER当作新版本的准确率证明。

## 手机内存与“页面不能卡死”的可实现边界

两轮原历史测试的 Paddle 整页观测PSS约1044.3、1031.1MiB；本轮诊断约911.5MiB。不同采样和运行条件有波动，不能保证任一台4GB手机可用，也不能把模型名中的mobile当作浏览器低内存保证。现有实验还硬编码 `mobile:false`、500万工作像素，不会自动继承正式Tesseract的手机150万像素预算。

建议先实现以下保护，并逐项验收：

- **隔离和停止：** 所有重型推理置于独立Worker；编辑页保持可编辑/导出。保存Worker句柄，主线程负责加载/推理超时和终止，异常时停止剩余批次，保留已完成记录。SDK `dispose()` 会等待Worker应答，不能将它当成对卡死推理可靠的硬取消；应有有限等待后的 `terminate()` 及待处理Promise拒绝逻辑。初始化也要有主线程看门狗，不能只包一个永远无法触发的同线程计时器。
- **限制并发和副本：** 同时只允许一个引擎/一张图/一个识别任务；图片用可转移对象或Blob传给Worker，识别后释放ImageBitmap、画布和Blob URL；显示用缩略图不常驻所有全分辨率解码图，批量上传不能等同批量解码。Word附原图是独立内存压力来源，不能只测试OCR。
- **输入预算：** 保留现有文件限制，增加在完整解码之前读取JPG/PNG尺寸的检查；当前 `inspectFile` 是先解码再查2500万像素，无法阻止解码时的内存峰值。手机Paddle可从现有150万工作像素档开始做工程验收，但这是待验证的产品预算，**不是本轮修改，也不能沿用500万像素的CER**；缩小会丢字时要显示实际尺寸并建议框较小区域。
- **能力提示：** 检查Worker/WASM/ImageBitmap/OffscreenCanvas；`navigator.deviceMemory` 仅作粗略提示，Safari常不可用，JS堆不含全部WASM/Worker内存。不可据此显示“剩余内存足够”或伪造实时总内存数字。未验证手机默认Tesseract，Paddle由用户明确选择。
- **失败文案：** 可捕获的内存分配失败可显示“浏览器内存不足，本页未完成识别。已有文字已保留；请框较小区域，或切换Tesseract后重试。”普通加载超时/Worker中断应显示“模型加载或识别中断，可能与下载、浏览器限制或内存有关”，不能一律断言内存不足。非空、空结果和失败状态分别记录，禁止伪装为空白页或静默改用另一引擎。
- **草稿恢复：** 建议文本/区域/已完成状态做小体积本地检查点（不默认保存图片，处理配额/隐私和写入失败），并允许随时导出。重载时可提示上次任务未完成，要求重新选择图片继续；本轮未实现持久化。

**无法承诺任何手机内存不足时都能显示提示。** 浏览器/操作系统可能直接杀掉整个渲染进程或重载页面，JavaScript没有机会捕获错误或显示消息；Worker同样共享设备内存。可以通过隔离、限额、硬取消、草稿恢复降低风险，但必须如实区分“可捕获失败有提示”与“系统杀页可恢复”，不能承诺绝不卡死。当前实验达不到这项产品要求，不能直接发布。

## 下一阶段建议顺序

1. 在独立实现分支只做生命周期/Worker/CSP/运行时版本处理，不动识别算法；先通过桌面和冻结样本输出对照。
2. 接入最小引擎选择、按需加载、整区几何阅读序及原始记录；保留Tesseract默认及全部导出/校对功能。
3. 完成真机矩阵和故障恢复，披露不能可靠捕获的系统杀页；不通过则限制手机Paddle范围。
4. 形成可审查的集成PR及测试证据后，再由仓库流程决定采纳。本轮仅提交评估文档和数字摘要，main和正式站不变。
