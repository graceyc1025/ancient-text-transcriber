# PaddleOCR.js + PP-OCRv5 浏览器可行性实验

日期：2026-10-15（北京时间）。实验分支：`experiment/paddleocr-v5-browser`，从 `fix/ocr-square-diagnosis` 的 `4a6c87d` 派生。**未改main、未自动合并、未部署正式网站；现有Tesseract及导出功能保留。**

## 结论

1. **免费、纯浏览器、静态托管路线可运行。** 官方PaddleOCR.js SDK在真实Chromium中，用单线程WASM完成PP-OCRv5移动版检测与识别。全部运行时和模型从同源静态文件加载，无API Key、付费API、Python后端、数据库或上传接口。
2. **尚不能证明更适合清代古籍。** 有完整真值的样本只有现代生成的繁体竖排30字和横排19字。Paddle在竖排整页正确29/30、三栏正确30/30；但Tesseract改用原尺寸后也有29/30，不能把相对默认2倍放大的差异全部归因于模型。没有具备版本来源和人工逐字真值的清代刻本、石印本、行草标准测试集。
3. **资源代价明显增加。** 竖排整页中Paddle观测浏览器进程树PSS峰值约796 MiB，Tesseract默认约438 MiB；本地无压缩静态响应体合计约54.40 MB对16.00 MB。不能据桌面成功承诺手机稳定。
4. **Pages结构兼容已做本地验证，线上稳定尚未验证。** 实测项目子路径、无跨源隔离、无WebGPU依赖、手机触屏模拟和模型缺失报错。没有发布实验站点，未做Android/iPhone/Safari/Firefox实机测试。

建议继续保持独立实验，暂不替换正式默认引擎。最有价值的下一步是整理有来源的清代真值页，以及在真实手机上测内存和长图，而不是继续用现代小图调参数证明“古籍准确率”。

## 实验实现与模型来源

代码全部在[experiments/paddle](../experiments/paddle/README.md)，独立package.json及lockfile。正式入口、根依赖、根Vite配置与Pages工作流未因实验改变。原型只有选择图片/引擎、真实识别、标准文本评分、保存原始JSON所需的最小控件，不是正式产品界面升级。

运行版本：官方 `@paddleocr/paddleocr-js` 0.4.2、ONNX Runtime Web 1.22.0、OpenCV.js 4.10.0-release.1；对照Tesseract.js 7.0.0、原有固定tessdata_best模型、非SIMD LSTM核心。

**本次权重是社区导出版，不是已验证与官方原始模型包完全相同的文件。** 官方BCE下载域名被当前云环境代理拒绝，不能把此事误报为Pages或引擎不支持。为完成真实推理，使用npm数据包 `pdfmarkdown-ppocrv5-models@1.0.0`，其内容来自 `PT-Perkasa-Pilar-Utama/ppu-paddle-ocr-models` 固定提交 `384182c7187c12d4ea181ae3b97c8b7e12089d9d`。

- npm包SHA-512完整性与发布元数据匹配。
- 检测权重为ORT格式，4,896,928字节，SHA-256 `30acfc4e21f2a23669d01a75aaeb92190f96874613108a0f7086bed264420abc`。
- 识别权重为ONNX格式，16,559,278字节，SHA-256 `d253c3cbee6e507828a5271a30ab0ec8ae7c2a99d0cc8e6f844fe380809d22b3`。
- 两个权重哈希与上游GitHub LFS指针相符，权重未修改。未获得官方BCE包，因此不能验证与其权重逐字节相同，也不能把结论推广到任意PP-OCRv5导出。
- 社区数据包的字典比官方字典多一个空项及尾部空格。官方SDK自行处理CTC空白类与尾部空格，不能直接照搬该字典。实验使用PaddleOCR固定提交 `dab3fe35379033fdcb2d0e9572fac0b36c9a9ebf` 的18,383项字典，SHA-256 `d1979e9f794c464c0d2e0b70a7fe14dd978e9dc644c0e71f14158cdf8342af1b`，不使用参考文本决定字符映射。
- 为SDK打包固定的inference.yml、字典及权重；ORT检测数据置于SDK约定的inference.onnx条目，ONNX Runtime已实测可自动识别实际格式。所有打包后SHA固定于[models.json](../experiments/paddle/models.json)。这是配置适配，不是使用模拟识别结果。

模型/SDK/字典适用Apache-2.0，ORT为MIT，其他依赖许可随实验保留。无OCR调用费用；仍需设备计算和静态资源流量，Pages沿用账号已有套餐及限制，不承诺托管无限或平台永久不变。

扫描来源沿用[前次报告](OCR排查与优化.md)，图片SHA-256随[本轮数据](PaddleOCR实验数据.json)记录。没有向任何远程OCR服务发送图片。扫描文件及其完整输出只留在忽略目录，不部署。

30字标准文本，三列自右至左：

```text
學而時習之不亦說乎
有朋自遠方來不亦樂乎
人不知而不慍不亦君子乎
```

横排标准为前两行。标准只在OCR结束后参与评分，**不传给引擎，不用于纠字、补字或改列序**。

CER =（替换S + 删除D + 插入I）/标准字符数N。正确字数为编辑距离对齐后的匹配数N−S−D。按Unicode码位比较，只忽略排版空白；不做简繁/异体等价、不去掉误识标点、不以汉字输出数量推算正确率。

比较原始候选，Tesseract阈值设0，Paddle识别分数过滤设0；不以是否标□代替质量指标。Paddle检测参数固定为长边上限960、max、DB阈值0.3、框阈值0.6、unclip1.5、batch1。Tesseract保留默认2倍放大对照，另做与Paddle同为原尺寸的控制；三栏使用相同等宽区域与共同Canvas裁切函数。两引擎内部缩放/解码仍不同，参数明示，不是完全相同算法。

### 繁体与阅读顺序

两引擎输出均未经简繁转换。Paddle在现代样例保留“學、習、說、慍、樂”等繁体，但模型字集覆盖不等于清代异体字保证；还可能自然误认成简体、日文字形或其他候选。

Paddle SDK整页原始顺序实际上是：

```text
人不知而不慍不亦君子乎
有朋自方來不亦樂乎
學而時習之不亦說乎
```

直接拼接SDK文本时，该图CER为56.67%，混入了列序错误。实验保留此原始输出，同时按几何坐标调整为右至左、同列上至下，才得到3.33%。**SDK不能直接当作已支持古籍右至左阅读顺序。** 分栏会改变检测和识别，不能根据参考文本挑选或补回候选。

SDK会将高宽比≥1.5的文字块逆时针旋转90度再识别；在本图可用，不代表夹注、双行小字、版心或行草均适用。DocPreprocessor和TextLineOrientation在该SDK版本发出“不支持、忽略配置”的提示，未假装启用了自动纠斜或方向分类。

## 时间、模型大小及浏览器内存

环境：Linux，Chromium 154.0.8037.57，AMD EPYC 9V74，云环境可见5个逻辑CPU、约34,088 MiB内存。15种配置各3次真实推理，共45次，全部完成，每种配置三次文字相同。

每个配置使用全新浏览器。初始化包括资源加载、解包、WASM/模型准备；推理计时另记，含该引擎实际裁切、预处理和解码。静态文件经本机回环网络、无压缩服务；**这些秒数不是用户首次访问Pages的网络耗时**。

| 竖排30字配置 | 初始化ms（一次） | 推理ms（三次中位数） | 观测PSS峰值MiB |
| --- | ---: | ---: | ---: |
| Tesseract整页2倍 | 492 | 785 | 438 |
| Tesseract整页原尺寸 | 462 | 679 | 409 |
| Paddle整页原尺寸 | 1,645 | 895 | 796 |
| Tesseract三栏2倍 | 454 | 805 | 417 |
| Tesseract三栏原尺寸 | 501 | 731 | 411 |
| Paddle三栏原尺寸 | 1,757 | 822 | 689 |

首轮推理另有JIT/缓存效应，例如Paddle整页首轮约1,426ms，后两轮更快；不可把单次暖运行当作端到端总耗时。

| 资源 | Tesseract竖排 | Paddle实验组合 |
| --- | ---: | ---: |
| 交付模型文件 | gzip 11,945,998字节；解压12,985,521字节 | SDK用tar合计21,572,608字节；其中权重21,456,206字节 |
| 该配置实际请求的唯一静态文件体积 | 约16.00 MB | 约54.40 MB |
| 主要额外运行时 | 原有LSTM WASM/Worker | OpenCV/SDK JS约10.48 MB，实际用ORT JSEP WASM约21.87 MB，另有ORT JS/mjs |

模型归档编码不同，不能简单把文件体积等同线上流量；Pages可能按响应头压缩，未在线测定。完整双引擎实验构建约129.7 MB，含两种Tesseract语言和未使用的SDK worker/重复ORT资源，**并非一次浏览器请求量**；实验尚未做产物瘦身。单个最大文件约21.9 MB，静态结构可容纳，但应在正式采纳前减少无用资源。

内存通过CDP定位**该浏览器全部进程**，每100ms读取Linux `/proc/.../smaps_rollup` 的PSS；包含原生、WASM、Worker及渲染进程，不把主页面JS堆冒充总内存。基线约235 MiB，表格为初始化和3次推理期间**采样到的峰值**，不是绝对峰值或设备保证。共享页、浏览器配置及采样开销会影响数值，不是实机手机内存测量。

## GitHub Pages、兼容性及实际遇到的问题

- 本地用GET/HEAD-only静态服务真实挂载 `/ancient-text-transcriber/experiments/paddle/`。HTML、ES模块、模型tar、ORT mjs/wasm全部同源，模型和库不从默认第三方CDN加载，上传图像不发送网络请求。
- 强制 `backend: wasm`、`numThreads: 1`、`proxy: false`、SDK main-thread模式，不依赖WebGPU或SharedArrayBuffer。实测 `crossOriginIsolated=false` 时可识别，服务未设置COOP/COEP；不用借助后端注入这些响应头。
- **真实遇到CSP阻碍**：OpenCV.js 4.10构建使用动态Function，仅有wasm-unsafe-eval会失败。实验页单独允许unsafe-eval；正式站点CSP保持原样。OpenCV内嵌WASM使用data:，实验connect-src允许本地data:。这是当前依赖组合的兼容代价，不能不经评估照搬到正式站点。
- ORT必须带匹配版本的mjs与wasm。本版本实际请求JSEP变体，即使后端选择CPU，也不能只拷贝非JSEP文件；两种文件均准备，实际请求已记录。
- 社区检测权重为ORT而非ONNX，需格式与版本兼容；已在本组合实测，不代表所有预序列化ORT或量化导出都适配。
- SDK main-thread推理时界面可能暂停，模型失败后的资源管理、取消和长时间批量任务尚未达到正式版水平。实验不实现批量产品流程，也不删原来的Tesseract网页。
- 已通过3组实验浏览器检查：桌面上传/识别/右至左/JSON；390×844触屏手机模拟真实Paddle推理；识别模型404时明确报错、无假文字或远程回退。所有HTTP请求同源GET/HEAD，正常场景无页面脚本异常及资源失败。
- 原项目18项单元测试、7组真实浏览器回归继续通过；独立实验3项单元测试、构建和锁文件重装复现通过。没有线上Pages验证、真实手机、Safari或Firefox验证。

因此可以说“该组合在静态项目子路径上已运行”，不能说“已在GitHub Pages上线”或“所有手机稳定”。约700–800 MiB级浏览器进程树内存观测值使低内存手机尤其需要真实测试；不通过时应保留Tesseract回退，不能把系统杀页当成无字页。

## 如果后续稳定性不满足，免费的选择

1. 保留现有Tesseract、手工分区及原图校勘；本轮原尺寸控制值得保留为实验选项，但不据现代图把正式缩放默认值改掉。
2. 继续使用同一组可验证的PP-OCRv5权重，以ONNX Runtime Web + 浏览器图像处理单独实现管线，或评估不依赖动态eval的OpenCV构建，降低SDK/打包负担。需要重新验证检测、裁切、字典、阅读顺序和内存，**本轮未实现，不承诺稳定或更准**。
3. 寻找有清代刻本/行草标注与开源权重的轻量模型，再独立验证ONNX/WASM可用算子及许可证。目前没有实测证据可推荐一个已经可靠优于现有方案的纯浏览器古籍模型。
4. Kraken等历史文献训练工具本身免费开源，但官方管线依赖Python/PyTorch，不能直接部署GitHub Pages；在当前“纯浏览器”约束下不作为现成替代，也不引入服务器。
